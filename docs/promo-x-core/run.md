## Running locally

Prerequisites: JDK 25 and Docker, and Keycloak running.

1. **Start PostgreSQL and Redis** from `promo-x-core`, with the [variables](#environment-variables) in
   `promo-x-core/.env`:

   ```bash
   cd promo-x-core
   docker compose -f docker-compose-dev.yaml up -d
   ```

2. **Export the variables** for the migration and the app (Spring doesn't read `.env` itself), then
   **apply the migrations**. Flyway runs through the Maven plugin, not at application startup:

   ```bash
   set -a; source .env; set +a
   ./mvnw flyway:migrate
   ```

3. **Run the application** on http://localhost:8000, with the `dev` [profile](#profiles):

   ```bash
   ./mvnw spring-boot:run -Dspring-boot.run.profiles=dev
   ```

If `./mvnw` isn't executable on your machine, run it as `sh mvnw`.

To run the packaged jar instead, as the servers do:

```bash
./mvnw package -DskipTests
SPRING_PROFILES_ACTIVE=dev java -jar target/promox-core.jar
```

## Environment variables

| Variable | Description |
|---|---|
| `SQL_HOST` | PostgreSQL host and port, e.g. `localhost:5432` |
| `SQL_DATABASE`, `SQL_USER`, `SQL_PASSWORD` | Application database and credentials |
| `POSTGRES_PASSWORD` | Superuser password of the dev PostgreSQL container (Docker Compose only) |
| `REDIS_HOST`, `REDIS_PASSWORD` | Redis host and port, e.g. `localhost:6379`, and its password |
| `IDP_ISSUER_URL` | JWT issuer, e.g. `http://localhost:8080/realms/<realm>` |
| `SQL_POOL_MAX_SIZE` | Database connections per instance (default 10). Size it for the database server, about (DB cores × 2) + disks, shared by all instances |
| `SQL_POOL_MIN_IDLE` | Idle connections kept open (defaults to `SQL_POOL_MAX_SIZE`, a fixed-size pool) |
| `SPRING_PROFILES_ACTIVE` | The [profile](#profiles): `dev`, `stage` or `prod` |

## Profiles

The profile names the environment in every log line (the `environment` field) and turns on a few local tools.

| Profile | `environment` in the logs | Also |
|---|---|---|
| `dev` | `dev` | Swagger UI at `/swagger-ui.html`, CORS for the dashboard at http://localhost:4200, Spring Security and Hibernate batch logs at DEBUG/TRACE |
| `stage` | `stage` | |
| `prod` | `production` | |
| none | `unknown` | |

A server should always run with `stage` or `prod`: `unknown` in the logs means the profile wasn't set.

## Logs

The application writes its logs to stdout, one JSON object per line, in the Logstash format. It doesn't write log
files: where the logs go is up to whatever runs the process (Docker, Elastic Beanstalk, Kubernetes). A stack trace is
a field of its line, not separate lines, so a log collector needs no multi-line rules.

```json
{"@timestamp":"2026-11-24T23:11:51.575Z","@version":"1","message":"Request failed with a server error","logger_name":"com.promox.core.infrastructure.logging.RequestLoggingFilter","thread_name":"tomcat-handler-0","level":"ERROR","level_value":40000,"traceId":"0af7651916cd43dd8448eb211c80319c","spanId":"75aaef10fdc375a0","userId":"5f1c9a1e-2b7d-4c3e-9f0a-8d6b2e4c7a11","requestId":"3b2f8c1e-6a4d-4e9b-8f7a-1c2d3e4f5a6b","httpMethod":"GET","path":"/api/storefront/7","handler":"StorefrontController#getStorefrontById","storefrontId":"7","status":500,"app_name":"promo-x-core","environment":"production","stack_trace":"java.lang.IllegalStateException: ..."}
```

### Fields

| Field | On | Meaning |
|---|---|---|
| `@timestamp` | Every line | When it was logged, in UTC |
| `level`, `level_value` | Every line | `ERROR`, `WARN`, `INFO`, `DEBUG`, `TRACE`, and its number for sorting |
| `logger_name`, `thread_name` | Every line | Where it was logged from: the class and the thread |
| `message` | Every line | What happened |
| `app_name` | Every line | `spring.application.name`: `promo-x-core` |
| `environment` | Every line | Set by the [profile](#profiles) |
| `stack_trace` | Lines with an exception | The exception and its causes |
| `requestId` | A request's lines | A new UUID per request, generated by the server, never taken from the caller. Also sent back in the `X-Request-Id` response header, for a caller to quote when reporting a problem |
| `traceId`, `spanId` | Request and job lines | Micrometer Tracing IDs. The trace ID is taken from an incoming W3C `traceparent` header, so it is shared with the calling service, or generated |
| `userId` | A request's lines, once the token is authenticated | The token's `sub` claim |
| `jobName`, `jobRunId` | A scheduled job's lines | The job, such as `promotion-rule-usage-expiration`, and a new UUID per run |
| `httpMethod`, `path`, `status`, `handler` | Request error and DEBUG lines | The request (path without the query string), its response status, and the controller method, such as `PromotionController#evaluatePromotionRules` |
| Path variables | Request error and DEBUG lines | The request's path variables under their own names, such as `storefrontId`, `promotionRuleId` or `usageId` |
| `errorType`, `reason` | 401 and 403 lines | Why the request was rejected, such as `InvalidBearerTokenException` and `Jwt expired at ...`. The token itself is never logged |
| `durationMs` | DEBUG "Request completed" lines | How long the controller took |
| Feature keys | Lines that add them | Values a feature logs with `log.atDebug().addKeyValue(...)`, such as the job's `expiredUsages` and `batches` |

### What is logged

| What | Level | Message |
|---|---|---|
| A request that failed with a 5xx status, with its stack trace | `ERROR` | `Request failed with a server error` |
| A request rejected with 401: no token, or an invalid or expired one | `WARN` | `Request rejected: authentication failed` |
| A request rejected with 403: the user lacks the role | `WARN` | `Request rejected: access denied` |
| A failed scheduled job run, with its stack trace | `ERROR` | `Scheduled job failed` |
| Each request a controller receives, and how it completed | `DEBUG`, off by default | `Request received`, `Request completed` |
| A scheduled job run's outcome | `DEBUG`, off by default | Such as `Expired the overdue rule usages` |

Client errors (other 4xx: validation, business rules, not found) aren't logged: the response already tells the
caller what was wrong.

`spring.jpa.show-sql` is on in `application.yaml`, so Hibernate also prints each SQL statement to stdout as plain
text (`Hibernate: select ...`), outside the JSON format. Turn it off (`SPRING_JPA_SHOW_SQL=false`) wherever the logs
are collected.

### Turning on DEBUG for a controller

The DEBUG lines of a controller are written under the controller's own logger, so they can be turned on for one
controller during an incident. The level is read at startup: set it, then restart the application. The actuator
`loggers` endpoint, which changes levels at runtime, isn't exposed.

For every controller in a package, an environment variable is enough:

```bash
LOGGING_LEVEL_COM_PROMOX_CORE_PROMOTION_INTERNAL_WEB=DEBUG
```

For one controller class, use `SPRING_APPLICATION_JSON` or a JVM option instead. An environment variable can't
name a class: Spring lowercases its name, and logger names are case-sensitive.

```bash
SPRING_APPLICATION_JSON='{"logging":{"level":{"com.promox.core.promotion.internal.web.PromotionController":"DEBUG"}}}'
# or
java -Dlogging.level.com.promox.core.promotion.internal.web.PromotionController=DEBUG -jar target/promox-core.jar
```

The scheduled job's DEBUG lines work the same way, under
`com.promox.core.promotion.internal.service.PromotionRuleUsageExpirationJob`.

### Reading the logs locally

The JSON is meant for log tools, not for reading in a terminal. Run the jar through `jq` to read it; the filter
keeps lines that aren't JSON as they are:

```bash
java -jar target/promox-core.jar | jq -R 'fromjson? // .'
```

Only the lines of one request, or only errors and warnings:

```bash
java -jar target/promox-core.jar | jq -cR 'fromjson? | select(.requestId == "3b2f8c1e-6a4d-4e9b-8f7a-1c2d3e4f5a6b")'
java -jar target/promox-core.jar | jq -cR 'fromjson? | select(.level == "ERROR" or .level == "WARN")'
```

### Docker

The application has no Dockerfile in this repository. In whatever image runs the jar, pass the profile and the
[variables](#environment-variables) as the container's environment, and leave the logs on stdout: Docker stores
them.

```bash
docker run -d --name promo-x-core -p 8000:8000 \
  --env-file .env -e SPRING_PROFILES_ACTIVE=prod \
  --log-opt max-size=50m --log-opt max-file=5 \
  <image>
```

Docker's default `json-file` log driver keeps every line forever unless `max-size` and `max-file` are set, as
above or in `/etc/docker/daemon.json`.

Reading them:

```bash
docker logs -f promo-x-core                                    # follow
docker logs --since 30m promo-x-core | jq -R 'fromjson? // .'  # the last 30 minutes, readable
docker logs promo-x-core | jq -cR 'fromjson? | select(.level == "ERROR")'
docker compose logs -f promo-x-core                            # when started with Docker Compose
```

To collect them centrally, either run a collector that reads the container logs (Fluent Bit, Vector, Grafana Alloy,
Filebeat) and parses each line as JSON, or set a log driver that sends them, such as `awslogs` for CloudWatch Logs.

### Elastic Beanstalk

Set the profile and the [variables](#environment-variables) as the environment's properties (Configuration →
Updates, monitoring, and logging → Environment properties), with `SPRING_PROFILES_ACTIVE=prod`.

Elastic Beanstalk stores what the process writes to stdout on each instance:

| Platform | File on the instance |
|---|---|
| Java SE (the jar) | `/var/log/web.stdout.log` |
| Docker | `/var/log/eb-docker/containers/eb-current-app/eb-<container ID>-stdouterr.log` |

Reading them:

- **From the console:** Logs → Request logs → Last 100 lines, or Full logs, for every instance.
- **With the EB CLI:** `eb logs` for the last lines of every instance, `eb logs --all` for the full files.
- **On an instance:** `eb ssh`, then `tail -f /var/log/web.stdout.log | jq -R 'fromjson? // .'`.

To keep them after an instance is replaced and search them across instances, stream them to CloudWatch Logs, in
the console (Configuration → Updates, monitoring, and logging → Instance log streaming to CloudWatch Logs) or with
`.ebextensions/logs.config`:

```yaml
option_settings:
  aws:elasticbeanstalk:cloudwatch:logs:
    StreamLogs: true
    DeleteOnTerminate: false
    RetentionInDays: 30
```

Each file becomes a log group, such as `/aws/elasticbeanstalk/<environment name>/var/log/web.stdout.log`. CloudWatch
Logs Insights detects the JSON fields, so they can be queried by name:

```
fields @timestamp, level, message, requestId, userId, path, status
| filter level = "ERROR" or level = "WARN"
| sort @timestamp desc
```

On the Java SE platform, the lines of `web.stdout.log` pass through the system log, which may put a timestamp and
`web[<pid>]:` in front of the JSON. Check a line of the file: with that prefix, Logs Insights doesn't detect the
fields, and the Docker platform, which stores the container's output as it is, is the simpler choice.

### Kubernetes

Set the profile and the [variables](#environment-variables) in the Deployment, the passwords from a Secret:

```yaml
containers:
  - name: promo-x-core
    image: <image>
    ports:
      - containerPort: 8000
    env:
      - name: SPRING_PROFILES_ACTIVE
        value: prod
    envFrom:
      - configMapRef:
          name: promo-x-core-config
      - secretRef:
          name: promo-x-core-secrets
```

Reading them:

```bash
kubectl logs -f deploy/promo-x-core                                     # one pod of the Deployment
kubectl logs -f -l app=promo-x-core --prefix --max-log-requests 10      # every pod, each line with its pod
kubectl logs --previous <pod>                                           # the pod's last container, after a crash
kubectl logs --since 30m deploy/promo-x-core | jq -cR 'fromjson? | select(.level == "ERROR")'
```

`kubectl logs` only reads what the node still holds for the running pods. To keep and search the logs, run a log
agent as a DaemonSet (Fluent Bit, Grafana Alloy, Vector, Elastic Agent). It reads every container's output from
`/var/log/containers/` on its node. The container runtime adds its own prefix (time, stream) to each line, which the
agent's CRI parser removes; then parse the message as JSON, so its fields can be searched by name.

To turn on [DEBUG for a controller](#turning-on-debug-for-a-controller), add `SPRING_APPLICATION_JSON` to the
Deployment's `env`; changing it restarts the pods.

## Traces

Every request and every scheduled job run gets a trace ID and a span ID, which the logs carry. The spans themselves
aren't exported: no tracing backend is needed, and nothing is sent anywhere.
